# 契约（contracts）

> 这六条是 binGPU 的"地基"。任何后端（CPU / Vulkan / D3D11 / D3D12 / GL）的实现取舍都不能破坏它们；
> 任何上层（bin2d / bin3d / binUI）都可以**依赖**它们来写自己的代码。
> 每条都写了"为什么"，因为这类约定只有在知道代价之后才守得住。

---

## 1. 只有一套绘制面：原语 + 状态，没有用户着色器

目前的绘制能力就是：四边形（`draw_quads`）、索引网格（`draw_indexed`）、十来个状态
（viewport / scissor / pipeline / texture / sampler / affine）。

**为什么**：这一层的目标是"同一件事只写一遍"，不是"再做一个 RHI"。用户着色器会立刻带来
着色器编译工具链、资源绑定反射、绑定的目标语言怎么描述 SPIR-V 等一整套问题 —— 那是
0.2.0 之后（bin3d 进 GPU 阶段时）才值得付的成本。固定管线先让四个后端有**唯一**的像素
定义，也让"跨后端逐像素一致"这件事可验证。

**推论**：需要新效果时，先看能不能用现有原语组合出来（binUI 的 `box-shadow` 是"一串同心
圆角环"、`text-shadow` 是"图集里烘另一张位图"），而不是加接口。

## 2. 帧模型：begin → record → present；交换链不做局部重绘

一帧的形状是固定的：

```
bingpu_frame_begin(swapchain, cmd, &target)   // target 是**借用**的纹理句柄
  bingpu_cmd_begin_render(cmd, {target, ...})
    ... draw ...
  bingpu_cmd_end_render(cmd)
bingpu_frame_end(swapchain, cmd)               // 提交 + 呈现
```

**为什么**：
- 交换链图像的内容**不保证跨帧保留**（Vulkan spec 明文；D3D12 的 present 之后同样是
  "未定义"）。任何"只重绘脏矩形"的优化都建立在"上一帧还在"这个错误假设上。
- 想让上层偶发地用"累积帧 + 脏矩形"提速，正确做法是自己建一个 `RENDER_TARGET` 纹理
  当累积目标（离屏渲染不受这条约束），present 时整块画到交换链上。
- 借用的 `target` 句柄有效期到 `frame_end` 为止，**不许 destroy**（销毁会返回
  `BGPU_ERR_STATE`）；它的所有权在交换链。

## 3. 颜色约定：直通进、预乘算、不开 sRGB

- 公共 API 里所有颜色（顶点色、clear color）都是 `0xAARRGGBB` **直通**（非预乘）。
- 混合发生在预乘域：片元进混合前先 `rgb *= a`（GPU 后端在着色器里做，CPU 后端在
  核心循环里做）。
- 纹理上传是直通像素；纹理/目标存储是预乘像素（见 `raster_rules.md` §9）。
- 帧缓冲**不启用 sRGB**。

**为什么**：直通是作者看到的颜色（`#80FF0000` 就是"半透明红"），预乘是唯一能做对所有
混合模式的表示。两者在边界上转换，中间不混用。不开 sRGB 是因为整条链路（binUI 的
GDI/GL/VK 三端）都是 8 位直通，一旦某个后端偷偷开了 sRGB 帧缓冲，同一份颜色会暗一截 ——
这类 bug 极难查，而且会让像素比对整体失效。

## 4. 失败降级：错误码 + 线程本地错误串，没有异常

- 每个可能失败的函数返回 `BgpuResult`；失败后 `bingpu_last_error()` **一定**非空，格式是
  `<函数>: <原因> (file:line)`，后端原话会被拼进 `<原因>`。
- 没有异常、没有 RAII。C 里析构失败没有补救手段，所以 `*_destroy` 一律 `void` 且**幂等**：
  无效句柄 / 重复销毁都是 no-op，清理路径永远不打断程序。
- 设备创建失败 = 没有设备句柄；上层应当降级（例如 bin2d 退回软件绘制），而不是崩。

**为什么**：这一层要给 Python/Go/Rust 直接绑，异常和"半构造对象"在跨语言边界上没有
对应物。错误串里带 `file:line` 是因为**绑定作者看不到 C 源码的调用栈**，他们只能看到
一行字符串 —— 那一行必须能定位到实现位置。

## 5. 没有回调：事件走 `bingpu_poll()`

设备丢失、交换链失效这类事件只有一个通道：外壳每帧调一次 `bingpu_poll(device, &ev)`，
队列空时返回 `BGPU_OK` + `kind == BGPU_EVENT_NONE`。

**为什么**：回调意味着"回调里又进 GPU 层"的可重入问题（撤销半帧状态、锁、句柄失效），
是 C ABI 上最贵的一类 bug。轮询把"事件什么时候处理"的决定权交回调用方，实现也可以把
事件攒到下一次 poll 一起给。

## 6. 单渲染线程；一个窗口只有一个呈现 API

- 所有 GPU 调用（含 `texture_upload` / `texture_read`）都在**同一个渲染线程**上。
  句柄表与资源状态没有加锁；错误槽用 `_Thread_local` 隔离，所以"别的线程读错误"是安全的，
  但"别的线程建纹理"不是。
- 一个 `native_window` 同一时刻只能绑一个呈现后端（交换链 present 与"读回 + GDI 贴屏"
  二选一）。多 API 共用一个 HWND 是未定义行为（`VK_KHR_win32_surface` Issue 2）。

**为什么**：上层（binUI/bin2d/bin3d）本来就是单线程记录、单线程提交；把多线程记录做进这一
层需要"记录期资源生命周期"和线程池，收益却是负的（2D UI 的绘制命令量级用不上）。等真有
需求，再在**上层**做并行记录、把每个 cmd 分给一个线程。

## 颜色 / 帧 / 像素：三个模型的关系

| 模型 | 定义在哪 | 谁依赖它 |
|---|---|---|
| 颜色模型（直通 ↔ 预乘、不 sRGB） | 本文 §3 | 所有后端 + 所有上层 |
| 帧模型（begin/record/present、不局部重绘） | 本文 §2 | 外壳循环、交换链后端 |
| 像素模型（中心采样、top-left、插值、混合） | [`raster_rules.md`](raster_rules.md) | 后端之间的逐像素比对 |

三者里只要有一条被某个后端"优化"掉，跨后端一致就不再成立。所以它们被写成了
**可执行规格**：像素模型由 `tests/test_cpu_render.c` 钉住，帧/错误模型由
`tests/test_abi.c` 钉住。
