# CPU 后端性能（perf）

> 目标：**四边形填充吞吐 ≥ 2×，行为逐位不变**。
> 结果：纯色填充 **4.6–7.3×**，裁剪内小批 **6.5×**，纹理路径 **1.6–2.3×**；
> `make bench` 的 13 个像素校验和与 0.2.0 **完全一致**，`test_abi` 239 + `test_cpu_render` 334
> 断言全绿。数字都在同一台机器（MinGW 15.1.0，x86-64，-O2/-O3）上量。

## 怎么量的

`make bench` 跑 `tools/bingpu_bench.c`：六类固定场景，每项先预热一次，再跑 5 次取**最好**
一次（排除调度抖动）。光栅场景渲到**离屏目标**，只计 `begin_render → draw → end_render`；
交换链的 `frame_end` 还会额外拷 4 MB（back→front），那是 ⑤ 的一部分，不摊到 ①~④ 上。

每个场景另外跑一遍"清 → 画 → 回读"，对回读字节做 FNV-1a —— 优化前后这 13 个数字必须
逐位相同。**这是"行为不变"的机器可查证据**，比人眼看图可靠。

表里的"基线"是 0.2.0（-O2，全 C++17 实现）在同一台机器上跑同一份 bench 的结果；
"现在"是 0.2.1，三次运行取每项最小值。同机复跑抖动约 ±10%（表取多次运行的最小值）。

## 改了什么（按收益排序）

### 1. 分路径 + 混合模式特化（最大一块）

0.2.0 的内层循环是"一条路径打天下"：不管画纯色还是纹理，每像素都要插值 `u/v/z`、
过一次管线的 `blend` switch、把目标像素读成 float（**每通道一次除 255**）、混合、
再乘回 255 取整。

- 不纹理就不算 `u/v`，不测深度就不插 `z`；
- 混合模式变模板参数，`switch` 提到三角形外，每条混合一条特化循环；
- **REPLACE / 预乘且源 alpha 正好 255 时不读目标**（`dst*0 = 0`，`src+0 = src`），直接写 4 字节。

收益：纯色 18.1 → 2.36 ms（**7.7×**），scissor 批 7.19 → 1.01 ms（**7.1×**），回读 3.62 → 2.36 ms。

### 2. 混合查表（KEEP / ERASE / ADDITIVE / 半透明预乘）

均匀色三角形的混合结果是"目标字节 → 结果字节"的纯函数，于是每个三角形预先算一张
**4×256 的置换表**，像素里只剩查表 + 写：

```
tbl[c][i] = q8(blend_one(src[c], 目标字节 i))     // 与逐像素路径同一条公式
```

表的每一项就是用同一条公式现算出来的，所以逐位一致；同一批小四边形往往同色同混合，
表还带缓存（`Paint::lut`）。

收益：KEEP 13.3 → 3.76 ms（3.5×，相对基线 **4.8×**），ERASE/ADDITIVE 同量级。
`test_cpu_render` 的五种混合精确像素断言是这条改动的护栏。

### 3. 采样器：状态外提 + 内联 floor + 取模快路径

- `TexState` 把尺寸/格式/filter/wrap/行跨距提到循环外（0.2.0 每像素都重新解引用 sampler）；
- `std::floor` 换内联实现（不带 `-fno-math-errno` 时它是一次 libm 调用，1024² 就是四百万次）；
- `wrap_index` 的 REPEAT 加"在范围内就不取模"的快路径（取模是整数除法）；
- 纹素按 `uint32` 取（4 字节格式），少四条字节加载。

收益：nearest 29.6 → 20.2 ms，linear 43.1 → 27.6 ms（在 1+2 之后的基础上）。

### 4. 均匀色三角形：整条片元计算提到循环外

三顶点同色（纹理时还要求同 UV）时，`src` 只算一次。为什么仍然逐位一致：插值结果是
`c·(w0+w1+w2)`，权重和与 1 的偏差在 1e-7 量级，而 8 位量化的余量是 0.5/255 ≈ 2e-3 ——
量化后必然是同一个字节。

### 5. 字节 ↔ float、反预乘都换查表

`i / 255.0f` 预先算成 256 项表（位模式与现算完全相同），反预乘预先算成 64 KiB 的
`(预乘值, alpha)` 表（`(p*255 + a/2)/a` 逐项同式）。回读 3.62 → 2.20 ms。

### 6. `-O3` 只给 `bingpu_cpu.cpp`

其余文件是冷路径（句柄表 / 校验 / 注册表），`-O3` 在那里收益为零。实测 UV 采样路径再快 ~20%。

## 没做的（以及为什么）

1. **边缘函数增量递推**（每行加一次 `de/dx` 代替 3×2 次乘法）：浮点累加会改变边函数的值，
   边界像素可能翻转 —— 与"逐位不变"冲突，放弃。
2. **行内 memset 快路径**（连续覆盖的像素直接铺）：覆盖率判定的浮点根与逐像素判定在
   退化的窄三角形上可能不一致。若要做，必须先证明"同一行内两个已覆盖像素之间的像素
   必然覆盖"在浮点下也成立（内点在精确数学下必然覆盖，但边函数在接近 0 时仍有舍入），
   属于需要单独设计与验证的一步，这一轮没做。
3. **SIMD（SSE2/AVX2）**：双线性要重排运算顺序才能打包，逐位一致的风险高；且当前瓶颈在
   分支（覆盖率）而不是纯算力。留待下一轮用"span 提取 + 4 像素一批"的方式做。
4. **纹理上传与 present 的 memcpy**：`frame_end` 的 4 MB 拷贝约占 ⑤ 的 1/3（0.4 ms 量级），
   已经是内存带宽极限，没有再动。
5. **多线程**：CPU 后端的定位是"可复现的像素裁判"，线程化会引入调度相关的非确定性，
   与定位冲突。

## 复现

```sh
mingw32-make clean && mingw32-make -j8 all
mingw32-make bench              # 表格 + 13 个校验和
mingw32-make bench 之外的单项：先看 tools/bingpu_bench.c 的场景定义，参数都写死
```

同机复跑抖动：表里的数字是"三次运行取每项最小"，单次 `make bench` 可能比表里高
10–15%（取决于当时机器上还有谁在跑）。拿数字做比较时请用同一台机器、同一轮；
`bingpu_bench` 内部已经是"5 次取最好"，外面不必再套循环。
